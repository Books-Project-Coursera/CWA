\section{Method}
\label{sec:method}

\subsection{The Rule}

A standard training run leaves behind one checkpoint per epoch,
$\mathbf{w}_1,\dots,\mathbf{w}_T$, and a validation score for each of them ---
the score the pipeline already computes in order to decide which checkpoint to
keep. Sort the checkpoints from best to worst by that score and write the
result $\mathbf{w}_{(1)},\dots,\mathbf{w}_{(T)}$, breaking ties in favour of
the later epoch. Conventional selection keeps $\mathbf{w}_{(1)}$ and discards
the rest. We keep the first $k$ and average them:
\begin{equation}
  \mathbf{w}_{\text{avg}}=\frac{1}{k}\sum_{i=1}^{k}\mathbf{w}_{(i)} .
  \label{eq:avg}
\end{equation}
That is the whole method. Averaging is element-wise and applies to trainable
parameters only. Setting $k{=}1$ gives back the baseline exactly, so the two
are the same procedure at two settings rather than two different procedures.
Increasing $k$ only adds one more checkpoint and never removes one already in
the average, since the top $k$ always contains the top $k{-}1$.

\subsection{What ``Best'' Means}

The rule needs one thing from the task: an ordering of the checkpoints. We take
whichever validation score the pipeline already uses for its own best
checkpoint, so nothing new is introduced and no threshold or weighting is
tuned. For classification that score is the validation loss and lower is
better. For detection and segmentation it is the validation fitness reported by
the Ultralytics trainer \cite{jocher2023ultralytics} --- a fixed combination of
mAP at IoU $0.5$ and averaged over $0.5{:}0.95$, summed over box and mask for
segmentation --- and higher is better. Only the sort direction differs, so the
same code runs on all three tasks.

Because \cref{eq:avg} depends on the scores only through the resulting order,
the rule is unaffected by any rescaling of the criterion, and it inherits
whatever the criterion is already good or bad at: if validation score is a poor
proxy for test performance, ranking by it will not fix that.

\paragraph{Normalization statistics.}
Batch-Normalization \cite{ioffe2015batch} running statistics are population
estimates tied to the particular weights that produced them, so the ones
inherited from any single checkpoint need not suit
$\mathbf{w}_{\text{avg}}$. Following SWA
\cite{izmailov2019averagingweightsleadswider} we reset them and recompute them
with forward passes over training data in training mode, without gradients or
optimizer updates.

\subsection{Cost}

\begin{algorithm}[t]
\caption{Top-$k$ checkpoint averaging}
\label{alg:topk}
\begin{algorithmic}[1]
\Require checkpoints $\mathbf{w}_1,\dots,\mathbf{w}_T$ and their validation
scores; aggregation size $k$; training data
\Ensure final model
\State sort the checkpoints best-first by validation score
\Statex \hfill\textit{(lower loss, or higher fitness; ties $\to$ later epoch)}
\State $\mathbf{w}_{\text{avg}} \gets$ average of the first $k$
\If{the model has BatchNorm layers}
  \State reset their running statistics and recompute them
  with forward passes over the training data, no gradients
\EndIf
\State \Return the model with weights $\mathbf{w}_{\text{avg}}$
\end{algorithmic}
\end{algorithm}

\Cref{alg:topk} is the procedure in full. Training is untouched, so training
cost is unchanged. Afterwards we pay $k$ tensor additions and one
recalibration pass, both negligible next to training, and the finished model
costs exactly one forward pass at inference.

Storage is the only real cost, and it is bounded: since only the order of the
scores matters, keeping a running set of the $k$ best checkpoints seen so far
gives the same result as sorting everything at the end, so $k{+}1$ states
suffice at any moment. Our detection and segmentation runs do exactly this,
deleting a checkpoint as soon as it drops out of the current top $k$; the
classification runs keep every epoch, and we report the counts in
\cref{sec:selection}.

\paragraph{Two implementation details.}
The Ultralytics trainer validates through an exponential moving average of the
weights by default. We turn that off, so the recorded fitness, the
early-stopping signal and the saved weights all refer to the same parameters ---
otherwise checkpoints would be ranked using weights other than the ones we
average. We also take the baseline from the top of the same ranking our rule
uses, rather than from the framework's exported best checkpoint, which is saved
at half precision: comparing that against a full-precision average would mix a
precision change into the comparison.
